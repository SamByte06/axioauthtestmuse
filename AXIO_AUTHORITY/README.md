# AXIOVITAL AUTHORITY

**The AxioVital platform control plane** — the central administrative authority used by
AxioVital personnel to govern the B2B healthcare partner network: partners, tenants,
operators, credentials, security policy, provisioning, integrations, and audit.

```
                         AXIOVITAL
                 GLOBAL HEALTHCARE PLATFORM
                            │
             ┌──────────────┼──────────────┐
            B2C            B2B            B2G
                            │
                            ▼
                     AXIOVITAL CLIENTS
                            │
                            ▼
                     AXIOVITAL NATIVE        ← clinical / operations plane
                     (data plane)               (patients, encounters, FHIR…)
                            │
                            ▼
                     AXIOVITAL BACKEND
                            │
                            ▼
              ┌──────────────────────────┐
              │  AXIOVITAL AUTHORITY     │  ← CONTROL PLANE (this repo)
              │  partners · tenants      │
              │  operators · credentials │
              │  policy · audit · status │
              └──────────────────────────┘
```

## What this is / is not

| AXIOVITAL AUTHORITY (control plane) | AxioVital Native (data plane) |
|---|---|
| Partners, tenants, operators | Patients, appointments, encounters |
| Credentials, access, policy | Clinical records, prescriptions |
| Provisioning, lifecycle, audit | Billing, insurance, reports, FHIR |

Authority administrators **do not** open patient clinical records. Clinical data access
remains separately authorized and audited. See `docs/architecture/control-plane-vs-data-plane.md`.

## Technology

- **Frontend:** Next.js 14 (App Router), React 18, TypeScript (strict), Tailwind CSS 3
- **Validation:** Zod
- **API:** REST over HTTPS against the AxioVital backend (`NEXT_PUBLIC_AUTHORITY_API_BASE_URL`)
- **Tests:** Vitest (unit/integration), Playwright (E2E for critical workflows)

The browser **never** connects directly to PostgreSQL, Redis, or infrastructure.
All provisioning, ID generation, and credential issuance are backend-authoritative.

## Getting started

```bash
# 1. Install
npm install

# 2. Configure the backend endpoint (never hardcode production URLs)
cp .env.example authority-frontend/.env.local
# edit NEXT_PUBLIC_AUTHORITY_API_BASE_URL

# 3. Develop / verify
npm run dev --workspace=authority-frontend
npm run typecheck --workspace=authority-frontend
npm run test:unit --workspace=authority-frontend
npm run build --workspace=authority-frontend
```

If `NEXT_PUBLIC_AUTHORITY_API_BASE_URL` is not set, the UI runs in
**unconfigured-backend mode**: every data view shows `Backend connection not
configured` instead of fabricated data. No fake success is ever shown.

## Security boundaries (non-negotiable)

1. No hardcoded credentials, no fake login, no frontend-only auth.
2. The browser never receives: DB/Redis/AWS credentials, private keys,
   JWT signing keys, Argon2 hashes, API secrets.
3. Credential state is displayed; credential *values* never are.
4. Partner IDs (`AXP-{STATE}-{LLDDDD}`) and Operator IDs
   (`AXO-{SUFFIX}-{TNNNNN}`) are generated by the backend only.
5. No patient clinical data in this application.
6. Frontend visibility is not the security boundary — the backend enforces RBAC.
