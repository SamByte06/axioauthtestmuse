# Security Boundaries

Non-negotiable rules for the Authority frontend. Every one is enforced by
code structure, not just convention.

## 1. The browser never receives secrets

The following must NEVER appear in an API response consumed by this
application, and therefore never in its UI, logs, or error messages:

- PostgreSQL credentials / connection strings
- Redis credentials
- AWS / S3 credentials
- Private keys (TLS, signing, card keys)
- JWT signing keys
- Argon2 / password hashes
- Database passwords
- API secrets / refresh tokens
- Enrollment / MFA secrets: `mfa_secret`, `mfa_qr_code_uri`, `enrollment_token` (see `docs/security/enrollment-secrets.md`)

The credentials domain exposes **state only**
(`PENDING_ENROLLMENT | ACTIVE | SUSPENDED | REVOKED | EXPIRED`).
Enrollment creates a workflow; it never returns a permanent secret to the
browser. Single-use enrollment URLs are masked by default and shown once.

## 2. The browser never connects directly to infrastructure (BFF Architecture)

The browser talks exclusively to its own origin via the server-side proxy (`/api/backend/*`).
The server-side proxy forwards to `BACKEND_API_BASE_URL` (a server-only environment variable).
- `connect-src` in the Content-Security-Policy strictly remains `'self'`.
- Upstream authentication tokens (JWTs) are exchanged server-side and kept in `HttpOnly; Secure; SameSite=Lax` session cookies; browser JavaScript never sees them.
- Mutating actions (POST, DELETE) enforce CSRF protection with Origin checks and custom client headers.
- Path traversal (`..`, `%2e`, `%2f`, `%5c`) and URI schemes are rejected at the proxy boundary.
- Upstream endpoints are strictly locked down to `/api/v1/admin/*` and `/api/v1/auth/*`.

## 3. No clinical data

Authority screens contain no patient records, encounters, prescriptions, lab
results, insurance documents, clinical reports, or medical images. See
`docs/architecture/control-plane-vs-data-plane.md`.

## 4. No fabricated platform state

- If the backend is unconfigured/unreachable, the UI says so. It never shows
  fake "healthy" infrastructure, fake partners, or fake success.
- Partner IDs, Tenant IDs, and Operator IDs are generated by the backend. The
  frontend validates displayed values and never invents them.
- `setTimeout`-based fake provisioning is forbidden. A success screen is
  rendered only after a real backend `2xx` for the whole transaction.

## 5. Destructive actions are gated

Suspend partner / suspend tenant / suspend operator / revoke operator /
revoke credential / revoke sessions require: confirmation dialog, stated consequence,
resource-identifier re-type, and an audit reason (≥10 chars). The backend
re-validates all of it and logs correlation IDs.

## 6. Audit is append-only

The frontend renders the audit log; it provides no edit/delete affordance,
and the backend must reject mutation of audit records.

## 7. Demo mode is strictly opt-in and non-production

Demo fixtures run only when `NEXT_PUBLIC_AUTHORITY_DEMO_MODE === "true"`
AND `NODE_ENV !== "production"` AND `NEXT_PUBLIC_VERCEL_ENV !== "production"`.
Production builds statically dead-code eliminate demo backends.
